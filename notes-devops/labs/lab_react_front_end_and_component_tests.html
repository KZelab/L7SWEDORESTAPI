React Front End and Component Tests

Overview

This lab gives the Notes product a face. You will build a one-page React front end in TypeScript that talks to the API from the Notes API and the Repository Pattern lab, so a user can add, edit and delete notes in a browser. You will then write component tests that render those components without a browser or a server, and use them to catch a defect you introduce on purpose.

Learning Objectives

By the end of this lab you will be able to:

  • Build a React front end that calls a REST API through a single API module
  • Explain how a development proxy lets a front end and a back end run as separate processes
  • Write component tests that find elements the way a user would, by label and role
  • Replace a module with a mock so that a component can be tested without a network
  • Judge what component tests with a mocked API do and do not prove

Concept

Checking a user interface by clicking through it works once. It does not scale to every change, and it does not happen at all when the person making the change is in a hurry. Without automated tests of the front end, a renamed button or a forgotten validation message reaches users unnoticed.

A component test renders one piece of the interface into a simulated page and interacts with it. Vitest runs the tests. happy-dom provides the simulated page, a lightweight version of the browser's document that lives inside Node.js with no window to draw. React Testing Library renders components into it and finds elements by what a user perceives: getByLabelText('Title'), getByRole('button', { name: 'Add note' }). A test written that way keeps passing when the markup is rearranged and fails when the experience changes. It also fails if a field has no label, which is an accessibility defect.

The components in this lab never call fetch themselves. They call functions in one module, api.ts. A mock is a stand-in that records how it was called and returns whatever the test tells it to. vi.mock('../src/api') replaces that whole module with mocks, so a test controls exactly what the "server" says. The price is that the real server is not involved. These tests prove the components behave correctly if the API behaves as the mock claims.

Task 2 - Put every API call in one module

Create a folder client/src, and in it api.ts. The private request() function handles the three things every call has in common: sending JSON, turning an error response into a thrown Error carrying the server's messages, and coping with a 204 response that has no body.

client/src/api.ts
export interface Note {
  id: string;
  title: string;
  body: string;
  createdAt: string;
  updatedAt: string;
}

export interface NoteInput {
  title: string;
  body: string;
}

async function request<T>(path: string, init?: RequestInit): Promise<T> {
  const response = await fetch(path, {
    headers: { 'Content-Type': 'application/json' },
    ...init,
  });

  if (!response.ok) {
    const problem = await response.json().catch(() => ({}));
    const errors: string[] = problem.errors ?? [];
    throw new Error(errors.join('. ') || `Request failed (${response.status})`);
  }

  // A 204 response has no body to parse.
  if (response.status === 204) {
    return undefined as T;
  }
  return (await response.json()) as T;
}

export function listNotes(): Promise<Note[]> {
  return request<Note[]>('/api/notes');
}

export function createNote(input: NoteInput): Promise<Note> {
  return request<Note>('/api/notes', {
    method: 'POST',
    body: JSON.stringify(input),
  });
}

export function updateNote(id: string, input: NoteInput): Promise<Note> {
  return request<Note>(`/api/notes/${id}`, {
    method: 'PUT',
    body: JSON.stringify(input),
  });
}

export function deleteNote(id: string): Promise<void> {
  return request<void>(`/api/notes/${id}`, { method: 'DELETE' });
}

Task 4 - Build the form component

Create client/src/components/NoteForm.tsx. The same form serves both adding and editing. When it is given initial values it is an edit form. When it is not, it is the create form and clears itself after a successful submit. Each input sits inside its label, which is what connects the visible word "Title" to the field.

client/src/components/NoteForm.tsx
import { useState } from 'react';
import type { FormEvent } from 'react';
import type { NoteInput } from '../api';

interface NoteFormProps {
  initial?: NoteInput;
  submitLabel: string;
  onSubmit: (input: NoteInput) => Promise<void> | void;
  onCancel?: () => void;
}

export function NoteForm({
  initial,
  submitLabel,
  onSubmit,
  onCancel,
}: NoteFormProps) {
  const [title, setTitle] = useState(initial?.title ?? '');
  const [body, setBody] = useState(initial?.body ?? '');
  const [error, setError] = useState('');

  async function handleSubmit(event: FormEvent) {
    event.preventDefault();
    if (title.trim().length === 0) {
      setError('Title is required');
      return;
    }
    setError('');
    await onSubmit({ title: title.trim(), body: body.trim() });
    // A form with no starting values is the create form, so clear it.
    if (!initial) {
      setTitle('');
      setBody('');
    }
  }

  return (
    <form className="note-form" onSubmit={handleSubmit} noValidate>
      <label>
        Title
        <input
          type="text"
          value={title}
          maxLength={100}
          onChange={(event) => setTitle(event.target.value)}
        />
      </label>
      <label>
        Body
        <textarea
          value={body}
          rows={3}
          maxLength={2000}
          onChange={(event) => setBody(event.target.value)}
        />
      </label>
      {error && (
        <p className="error" role="alert">
          {error}
        </p>
      )}
      <div className="actions">
        <button type="submit">{submitLabel}</button>
        {onCancel && (
          <button type="button" className="secondary" onClick={onCancel}>
            Cancel
          </button>
        )}
      </div>
    </form>
  );
}

Task 5 - Assemble the page

Create client/src/App.tsx. It holds the list of notes, loads them once when the page opens, and updates its own copy after each successful API call. The attempt() helper gives every action the same error handling.

client/src/App.tsx
import { useEffect, useState } from 'react';
import { createNote, deleteNote, listNotes, updateNote } from './api';
import type { Note, NoteInput } from './api';
import { NoteForm } from './components/NoteForm';
import { NoteList } from './components/NoteList';

export function App() {
  const [notes, setNotes] = useState<Note[]>([]);
  const [editing, setEditing] = useState<Note | null>(null);
  const [loading, setLoading] = useState(true);
  const [error, setError] = useState('');

  useEffect(() => {
    listNotes()
      .then(setNotes)
      .catch((problem: Error) => setError(problem.message))
      .finally(() => setLoading(false));
  }, []);

  // Runs an API call and shows its error message if it fails.
  async function attempt(action: () => Promise<void>) {
    try {
      setError('');
      await action();
    } catch (problem) {
      setError((problem as Error).message);
    }
  }

  function handleCreate(input: NoteInput) {
    return attempt(async () => {
      const created = await createNote(input);
      setNotes((current) => [...current, created]);
    });
  }

  function handleUpdate(input: NoteInput) {
    return attempt(async () => {
      if (!editing) return;
      const updated = await updateNote(editing.id, input);
      setNotes((current) =>
        current.map((note) => (note.id === updated.id ? updated : note)),
      );
      setEditing(null);
    });
  }

  function handleDelete(target: Note) {
    return attempt(async () => {
      await deleteNote(target.id);
      setNotes((current) => current.filter((note) => note.id !== target.id));
      if (editing?.id === target.id) {
        setEditing(null);
      }
    });
  }

  return (
    <main>
      <h1>Notes</h1>

      <section aria-labelledby="form-heading">
        <h2 id="form-heading">{editing ? 'Edit note' : 'Add a note'}</h2>
        {editing ? (
          <NoteForm
            key={editing.id}
            initial={{ title: editing.title, body: editing.body }}
            submitLabel="Save changes"
            onSubmit={handleUpdate}
            onCancel={() => setEditing(null)}
          />
        ) : (
          <NoteForm key="new" submitLabel="Add note" onSubmit={handleCreate} />
        )}
      </section>

      {error && (
        <p className="error" role="alert">
          {error}
        </p>
      )}

      <section aria-labelledby="list-heading">
        <h2 id="list-heading">Your notes</h2>
        {loading ? (
          <p>Loading notes...</p>
        ) : (
          <NoteList notes={notes} onEdit={setEditing} onDelete={handleDelete} />
        )}
      </section>
    </main>
  );
}

import type { Note } from '../src/api';
import { NoteList } from '../src/components/NoteList';

const milk: Note = {
  id: '1',
  title: 'Milk',
  body: 'Two pints',
  createdAt: '2026-01-01T00:00:00.000Z',
  updatedAt: '2026-01-01T00:00:00.000Z',
};

describe('NoteList', () => {
  it('shows a message when there are no notes', () => {
    render(<NoteList notes={[]} onEdit={vi.fn()} onDelete={vi.fn()} />);

    expect(screen.getByText(/No notes yet/)).toBeInTheDocument();
  });

  it('shows the title and body of each note', () => {
    render(<NoteList notes={[milk]} onEdit={vi.fn()} onDelete={vi.fn()} />);

    expect(screen.getByRole('heading', { name: 'Milk' })).toBeInTheDocument();
    expect(screen.getByText('Two pints')).toBeInTheDocument();

    await user.click(screen.getByRole('button', { name: 'Edit Milk' }));
    await user.click(screen.getByRole('button', { name: 'Delete Milk' }));

    expect(onEdit).toHaveBeenCalledWith(milk);
    expect(onDelete).toHaveBeenCalledWith(milk);

Task 12 - Evaluate

All 13 tests pass. Name a defect that could still stop a real user creating a note, which none of these tests would detect.

Anything at or beyond the boundary of the mock. Examples: api.ts sends the request to the wrong path or with the wrong method, the server rejects a field name the client sends, the proxy is misconfigured, or the server is not running. The App tests replace api.ts entirely, so a mistake inside api.ts or a disagreement between client and server about the shape of a note is invisible to them.

The tests find elements with getByLabelText and getByRole, not by CSS class or id. Give one advantage and one cost of that choice.

Advantage: the tests describe what a user perceives, so restructuring the markup or renaming a class does not break them, and a missing label or wrong role fails the test, which catches a real accessibility defect. Cost: changing visible wording, such as the text on a button, breaks tests even though nothing is functionally wrong, so copy changes need matching test changes.

Why is the development proxy useful, and what would have to be configured instead if the front end called http://localhost:3000 directly?

With the proxy the browser only ever talks to one origin, so the front end uses relative paths such as /api/notes and behaves the same wherever it is hosted. Calling the API on a different port directly is a cross-origin request. The server would need to send CORS headers allowing the front end origin, and the front end would need a configurable API address for each environment.
