Continuous Integration with GitHub Actions

Overview

Every check built so far, the linter, the unit and integration tests, the coverage gates, the browser tests, the image build and the vulnerability scan, only runs when somebody remembers to run it. This lab hands that job to a machine. You will write a GitHub Actions workflow that runs all of them on every pull request, watch it stop a broken change, and then change the rules on main so that nothing can be merged until the pipeline is green.

Learning Objectives

By the end of this lab you will be able to:

  • Write a GitHub Actions workflow with several jobs and explicit dependencies between them
  • Explain why a pipeline is ordered from the fastest checks to the slowest
  • Diagnose a failed pipeline run from its logs and artefacts
  • Require passing status checks before a pull request can be merged
  • Evaluate what continuous integration guarantees and what it leaves to people

Concept

A check that depends on memory and goodwill is skipped exactly when it matters most: late, under pressure, on the change that "obviously cannot break anything". It also runs on one developer's machine, with that machine's versions and leftovers, so a pass there says little about anywhere else.

Continuous integration means every change is merged into a shared line of work frequently, and every change is built and tested automatically by a neutral machine first. In GitHub Actions the automation is a workflow, a YAML file in .github/workflows. An on section names the events that start it. A workflow contains jobs. Each job runs on a fresh virtual machine called a runner and is a list of steps. A step either runs shell commands with run or calls a reusable action with uses.

Jobs run in parallel unless one declares needs, which makes it wait for others and be skipped if they fail. That is how a pipeline fails fast: quick, cheap checks go first, and slow, expensive ones only run on changes that have earned it. A step fails when its command exits with a non-zero code, which is why the coverage gate from the Back End Tests and Coverage Gates lab and --exit-code 1 on the scanner matter. Each job reports a status check on the pull request, and a ruleset can require those checks to pass.

Tasks

Task 1 - Start a branch

Create an issue named Run every check on every pull request, move it to In progress, and start a branch. Before you do, confirm that server/package-lock.json, client/package-lock.json and e2e/package-lock.json are committed. The pipeline installs from them.

git switch main

git switch -c ci/github-actions

Task 2 - Write a workflow with one job

Create the folders .github/workflows in the root of the repository, and in the inner one a file named ci.yml. Indentation is part of YAML's syntax. Use two spaces per level and never tabs.

  • on: pull_request starts the workflow whenever a pull request targeting main is opened or updated.
  • permissions: contents: read limits what the workflow's own access token may do to reading the repository. A pipeline should hold the least authority that lets it work.
  • defaults makes every run step in the job start in the server folder.
  • actions/setup-node installs Node.js 22 and caches downloaded packages between runs, keyed on the lock file.
  • The steps are the commands you have been running by hand, in order from fastest to slowest.
.github/workflows/ci.yml
name: CI

on:
  pull_request:
    branches: [main]

permissions:
  contents: read

jobs:
  server:
    name: Server checks
    runs-on: ubuntu-latest
    defaults:
      run:
        working-directory: server
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 22
          cache: npm
          cache-dependency-path: server/package-lock.json
      - run: npm ci
      - name: Lint
        run: npm run lint
      - name: Format check
        run: npm run format:check
      - name: Type check
        run: npm run typecheck
      - name: Unit tests
        run: npm run test:unit
      - name: Integration tests
        run: npm run test:integration
      - name: Coverage gate
        run: npm run test:coverage
      - name: Dependency audit
        run: npm audit --omit=dev --audit-level=high

Task 3 - Open a pull request and watch the pipeline

git add .github
git commit -m "Add CI workflow with server checks"
git push -u origin ci/github-actions

Open a pull request from the branch. Do not merge it. Scroll to the checks section at the bottom of the pull request, or open the Actions tab, and click into the running job.

Success condition: a job named Server checks runs each step in turn and finishes with a green tick. Expand the Coverage gate step. The same coverage table you saw on your own machine was produced on a machine you have never touched.

If the run fails on Format check, run npm run format in the server folder, commit and push. The pull request reruns the pipeline by itself.

Task 4 - Add the client job

Open .github/workflows/ci.yml and add a second job below the first. client: must line up exactly with server:, two spaces in from the margin. This job has no needs, so it runs at the same time as the server job on a separate runner.

.github/workflows/ci.yml
client:
    name: Client checks
    runs-on: ubuntu-latest
    defaults:
      run:
        working-directory: client
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 22
          cache: npm
          cache-dependency-path: client/package-lock.json
      - run: npm ci
      - name: Lint
        run: npm run lint
      - name: Format check
        run: npm run format:check
      - name: Unit and component tests with coverage gate
        run: npm run test:coverage
      - name: Build
        run: npm run build
      - name: Dependency audit
        run: npm audit --omit=dev --audit-level=high

Commit and push. Success condition: the pull request now shows two checks running side by side, and both go green.

Task 5 - Add the browser tests job

Add a third job. needs: [server, client] makes it wait for both earlier jobs and skips it if either fails. There is no point spending a minute downloading a browser to test code that does not pass its unit tests.

Complete the three TODO entries.

  1. Install dependencies. Three lines, one per project: npm ci --prefix server, and the same for client and e2e.
  2. Build the app. Two lines: npm run build --prefix client, then the same for server.
  3. Run Playwright. npx playwright test.

The last step uploads the Playwright report as an artefact, a file kept with the run that you can download. if: ${{ !cancelled() }} makes it run even when the tests failed, which is exactly when you want the report.

.github/workflows/ci.yml
e2e:
    name: Browser tests
    runs-on: ubuntu-latest
    needs: [server, client]
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 22
      - name: Install dependencies
        run: |
          # TODO: npm ci for server, client and e2e, using --prefix
      - name: Build the app
        run: |
          # TODO: build the client, then the server, using --prefix
      - name: Install Chromium
        working-directory: e2e
        run: npx playwright install --with-deps chromium
      - name: Run Playwright
        working-directory: e2e
        run: # TODO
      - name: Upload the Playwright report
        if: ${{ !cancelled() }}
        uses: actions/upload-artifact@v4
        with:
          name: playwright-report
          path: e2e/playwright-report
          retention-days: 7

Commit and push. Success condition: a Browser tests check appears, waits for the first two, then passes with 7 passed in its log. --with-deps installs the system libraries Chromium needs, which a fresh runner does not have.

Task 6 - Add the image job

Add the final job. It builds the image exactly as you did in the Containerising the Application lab, stamps it with the commit identifier as its version, and scans it. github.sha is the full identifier of the commit being tested. The image is built and scanned but not stored anywhere. This job only proves that it can be built and is safe to ship.

.github/workflows/ci.yml
image:
    name: Image build and scan
    runs-on: ubuntu-latest
    needs: [e2e]
    steps:
      - uses: actions/checkout@v4
      - name: Build the image
        run: docker build --build-arg APP_VERSION=${{ github.sha }} -t notes-devops:${{ github.sha }} .
      - name: Scan the image with Trivy
        run: |
          docker run --rm \
            -v /var/run/docker.sock:/var/run/docker.sock \
            ghcr.io/aquasecurity/trivy:latest image \
            --severity HIGH,CRITICAL --ignore-unfixed --exit-code 1 \
            notes-devops:${{ github.sha }}

Commit and push. Success condition: four checks, ending with Image build and scan, all green. Note the total time from push to the last green tick.

Task 7 - Push a defect and watch the pipeline stop it

Open server/src/routes/notes.ts and change the status code that POST returns for a new note from 201 to 200. It is a plausible slip, and the application still appears to work.

Commit and push it to the same branch.

git commit -am "Change create status code"
git push

Success condition: Server checks fails with a red cross. Open it. The lint, format, type check and unit test steps are green. The failure is in Integration tests, and the log names the test, creates a note and returns it with 201, and shows expected 200 to be 201. Browser tests and Image build and scan show as skipped. They never ran.

Consider what just happened. The unit tests could not see this defect, because no single function is wrong. The integration test caught it within a minute, and the two slowest jobs cost nothing.

Restore 201, commit and push, and wait for four green checks.

Task 8 - Make the checks mandatory

At the moment a red pipeline is only advice. The merge button still works. Change that.

  1. Open Settings, Rules, Rulesets, and edit the protect-main ruleset from the Agile Setup and Git Workflow lab.
  2. Turn on Require status checks to pass.
  3. Add all four checks by name: Server checks, Client checks, Browser tests, Image build and scan. GitHub only offers checks it has already seen run, which is why this step comes after the first pipeline runs.
  4. Turn on Require branches to be up to date before merging, then save.

Success condition: return to the pull request. The merge box now lists the four checks as Required. Merge the pull request, closing the issue. It is the first change in this project that could not have been merged broken.

git switch main
git pull

Task 9 - Evaluate

The pipeline was green and the change was merged. List three kinds of defect that could still have reached main.

Anything no test checks for: a missing feature or a misunderstood requirement, behaviour in a browser other than Chromium, performance or memory problems, security flaws that are not known vulnerabilities in a dependency, accessibility barriers a scanner cannot detect, and anything specific to the production environment such as configuration or data. A green pipeline means the checks that exist passed. It is evidence, not proof.

Server checks and Client checks run in parallel, while Browser tests waits for both. Explain the reasoning, and one way the arrangement could be made faster at the cost of something else.

The two fast jobs are independent, so running them together gives the earliest possible feedback. The browser job is slow and its result is meaningless if the faster checks fail, so making it wait saves runner time and keeps the failure signal clear. It could be made faster overall by running everything in parallel, at the cost of wasted minutes on doomed runs and several red checks for one cause, or by reusing build output between jobs, at the cost of a more complicated workflow.

Every job installs its dependencies from scratch on a brand new virtual machine. Is that a weakness or a strength of the design?

Both, and a good answer says so. It is slower than reusing a machine, and the repeated work costs minutes. It is also the main guarantee the pipeline offers: nothing is left over from a previous run, so a pass cannot depend on a stale file or a package somebody installed by hand. The build is proven reproducible from the repository alone. Caching recovers some of the speed without giving up that property.
