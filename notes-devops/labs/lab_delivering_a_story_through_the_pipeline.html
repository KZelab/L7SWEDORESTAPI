ACCA7023 - Agile and DevOps

Delivering a Story Through the Pipeline

Overview

Everything is now in place: a backlog, a protected main branch, four layers of tests, a container image, a pipeline that checks every change, and automatic deployment with rollback. This lab uses all of it for its real purpose. You will take the Search notes story from the backlog and deliver it to the live site without being given the code, then hold a short retrospective on what the pipeline did for you and what it did not. There is no solution to reveal. The evidence that you succeeded is a green pipeline and a working feature at your public address.

Learning Objectives

By the end of this lab you will be able to:

  • Refine a user story into acceptance criteria precise enough to test
  • Choose a design and justify which test layers the change needs
  • Deliver a change test-first through a pull request, a pipeline and an automatic deployment
  • Verify a feature in production and identify it by revision
  • Reflect critically on a delivery process using evidence from its own history

Concept

A pipeline that has only ever carried its own set-up has not been tested. The earlier labs each changed one thing at a time, with the answer close to hand. Real work is a story from the backlog that touches several parts of the system at once, where the first decision is not how to write the code but what "done" means and how you will know.

Test-driven development orders the work to answer that question first. Write a test for the next small piece of behaviour and watch it fail, which proves the test can detect the absence of the feature. Write the least code that makes it pass. Tidy up while the tests protect you. The cycle is often called red, green, refactor. Choosing which layer a test belongs to is a design decision: a rule belongs in a fast unit or component test, a contract between client and server belongs in an integration test, and one end-to-end test per story proves the pieces meet.

A definition of done is the team's shared checklist for calling a story finished. For this project it is no longer "it works on my machine". It is: acceptance criteria covered by tests, pipeline green, merged, deployed, and seen working in production. A retrospective then looks back at how the work went, using evidence, and agrees one or two changes to the process. It is how a team improves its way of working and not only its product.

Tasks

Task 1 - Refine the story

Open the Search notes issue on your board. At the moment it is one sentence. Before any code, edit the issue so that it contains:

  1. The story in full: as a user, I can search my notes, so that...
  2. At least four acceptance criteria in "Given, when, then" form. Decide and write down the answers to these questions, because a test will need them. Does search look at titles, bodies, or both? Is it case sensitive? What is shown when nothing matches? What happens when the search box is cleared? Does adding a note while a search is active show the new note?
  3. One thing that is explicitly out of scope, so the story has an edge.

Move the card to In progress and start a branch.

git switch main
git pull
git switch -c feature/search-notes

Task 2 - Choose a design and plan the tests

There are two reasonable designs. Choose one and write two or three sentences in the issue explaining why.

Filter in the browserFilter in the API
HowThe page already holds every note. A search box filters the list before it is displayed.The page sends the search text to the API, for example GET /api/notes?q=milk, and displays what comes back.
Files likely to changeApp.tsx, possibly a new componentThe repository interface and its implementation, the notes route, api.ts, App.tsx
Think aboutWhat if there were 50,000 notes?What does each keystroke cost? What does the repository interface now promise?

Then list, in the issue, the tests you intend to write and the layer each belongs to. Every acceptance criterion should map to at least one test. Use the lowest layer that can prove each criterion, and plan exactly one new end-to-end test for the story as a whole.

Task 3 - Red

Pick the first acceptance criterion. Write the test for it, at the layer you planned, before writing any of the feature. Model it on the existing tests in that folder.

Run that layer's tests.

Success condition: your new test fails, and it fails for the right reason. "Unable to find a label with the text Search" is the right reason, because the feature does not exist. A syntax error or a typing mistake in the test is not. All the existing tests still pass.

Task 4 - Green, then refactor

Write the least code that makes the failing test pass. Then take the next criterion and repeat: a failing test first, then the code. Work through all of your criteria this way.

Two things to keep in mind from earlier labs.

  • The search box is a form field. It needs a visible label, both for users and because your tests should find it with getByLabelText.
  • If you chose the API design, the routes must keep depending on the NoteRepository interface. Add the capability to the interface, then to the implementation.

When every criterion has a passing test, read your new code once more and tidy anything you would not want to explain in a review. Run the tests after each tidy-up.

Task 5 - Prove the story end to end

Add one test to e2e/tests/notes.spec.ts that follows the story as a user would: create two notes with different unique titles, search for one, and expect that one to be visible and the other not. Remember that the browser tests run against built code and share one server.

npm run build --prefix client
npm run build --prefix server
cd e2e
npx playwright test
cd ..

Success condition: 8 passed, including both accessibility tests. If an accessibility test now fails, read which rule it names. A search box without a label is the most likely cause.

Task 6 - Run everything the pipeline will run

Finding a failure on your own machine takes seconds. Finding it in the pipeline takes minutes. Run the full set before you push.

cd server
npm run lint && npm run format:check && npm run typecheck && npm run test:coverage
cd ../client
npm run lint && npm run format:check && npm run test:coverage && npm run build
cd ..

Success condition: every command succeeds. If a coverage gate fails, the table shows which of your new lines no test reaches. That is a missing test, not a reason to lower the threshold.

Task 7 - Deliver it

git add .
git commit -m "Add note search"
git push -u origin feature/search-notes
  1. Open a pull request. In the description write Closes #N for the story, and paste your acceptance criteria as a checklist, ticking each one a test covers.
  2. Move the card to In review. Read your own Files changed tab from top to bottom before the checks finish.
  3. When all four checks are green, merge. Note the time.
  4. Watch the Deploy run through to a green Smoke test.
  5. Open your public address and use the feature. Note the time again.

Success condition: search works on the live site, /api/health reports the merge commit as the version, the story closed itself, and its card is in Done.

If the pipeline went red at any point, do not treat that as a failure of the lab. Record what it caught. You will need it in the next task.

Task 8 - Hold the retrospective

Create docs/retrospective.md on a new branch and deliver it through a pull request like any other change. Base every statement on something you can point to: a pipeline run, a commit, a timestamp, a card on the board. Cover these headings.

  1. What the pipeline caught. List each time, across the whole practical, that an automated check stopped or would have stopped a defect. Name the check and the layer.
  2. What the pipeline missed. List anything that was wrong and reached main or production anyway, and anything you only found by looking. For each, say which kind of check could have caught it, or why none could.
  3. Flow. Give your measured time from merge to live, and from "started the story" to "live". Where did the time go? What was waiting, and what was work?
  4. Known limitations. State plainly what is still wrong with the product and the process. The in-memory store is one. Find at least two more.
  5. One change. Choose the single change to the process that you would make first, and justify it against the alternatives you considered.

Task 9 - Evaluate

You wrote each test before the code it tests. What did that order give you that writing the same tests afterwards would not have?

Evidence that each test can fail. A test written after the code has only ever been seen passing, so it may be checking nothing. Writing it first also forces the acceptance criterion to be precise before any design is committed, keeps the code to what a test demands, and means the feature is never in a state of working but untested. The cost is slower progress at the start and tests that may need rewriting if the design changes.

Compare the two search designs against the test layers you have. Which design is cheaper to test thoroughly, and does that make it the better design?

Browser filtering is cheaper to test: its rules sit in one place and component tests cover them quickly, with one end-to-end test on top. API filtering spreads the behaviour across repository, route and client, needing unit, integration, component and end-to-end tests to cover the same criteria, and it changes the repository interface. Cheaper to test does not settle it. Browser filtering stops being viable when the page cannot hold every note. Testability is one cost to weigh against scale and where the logic belongs.

Based on your retrospective, what is the weakest part of this delivery process, and what evidence supports that?

A strong answer picks one weakness and supports it with something recorded. Typical candidates: a sole developer approving their own pull requests, so nothing is independently reviewed. State held in memory, so every deployment destroys user data. Browser tests limited to one browser. No monitoring or alerting after the smoke test, so a failure an hour later goes unnoticed. No measure of whether a change was actually wanted. The quality of the answer lies in the evidence and the reasoning, not in which weakness is chosen.
