Back End Tests and Coverage Gates

Overview

This lab gives the Notes API two layers of automated tests and then makes the amount of testing a rule. Unit tests check the repository, the validation rules and the factory on their own. Integration tests send real HTTP requests through the whole Express application. You then measure how much of the code those tests execute, set a minimum, and watch that minimum reject a test suite that falls short. Applying the same rule to the front end from the React Front End and Component Tests lab exposes a module nobody had tested.

Learning Objectives

By the end of this lab you will be able to:

  • Write unit tests that check one class or function in isolation
  • Write integration tests that exercise routes, status codes and JSON shapes through the real application
  • Explain why each test needs its own fresh application and store
  • Measure line, branch and function coverage and read the report
  • Enforce a coverage threshold and judge what a coverage figure does and does not prove

Concept

The API was checked by hand with curl. That proved it worked on one afternoon. Nothing stops a later change breaking the 404 on a missing note, and nobody will retype eight curl commands after every edit to find out.

A unit test checks one small piece with nothing else attached. It runs in milliseconds and, when it fails, points at one function. It cannot tell you whether the pieces fit together. An integration test checks several pieces working as one. Here that means the router, the JSON parser, the validation, the repository and the error handler. Supertest makes this cheap. request(app) takes the Express application object and sends it requests directly, with no network port and no running server. Because createApp() accepts its repository as an argument, each test builds a new application around a new empty store, so no test can be affected by what another one left behind. That property is called test isolation.

Code coverage records which lines, branches and functions ran while the tests ran. A coverage threshold turns the measurement into a pass or fail result: the test command exits with an error if coverage is below the minimum. Coverage shows what was executed, not what was checked. A line that ran inside a test with no assertions counts as covered.

Task 2 - Unit test the repository

Create a folder server/tests/unit, and in it InMemoryNoteRepository.test.ts. beforeEach gives every test a brand new repository. Read each test name as a sentence that starts with "InMemoryNoteRepository". Together they are a specification of the class.

server/tests/unit/InMemoryNoteRepository.test.ts
import { beforeEach, describe, expect, it } from 'vitest';
import { InMemoryNoteRepository } from '../../src/repositories/InMemoryNoteRepository';

describe('InMemoryNoteRepository', () => {
  let repository: InMemoryNoteRepository;

  beforeEach(() => {
    repository = new InMemoryNoteRepository();
  });

  it('starts empty', async () => {
    expect(await repository.findAll()).toEqual([]);
  });

  it('creates a note with an id and timestamps', async () => {
    const note = await repository.create({ title: 'Milk', body: 'Two pints' });

    expect(note.id).toEqual(expect.any(String));
    expect(note.title).toBe('Milk');
    expect(note.body).toBe('Two pints');
    expect(note.createdAt).toBe(note.updatedAt);
  });

  it('finds a note by id', async () => {
    const created = await repository.create({ title: 'Milk', body: '' });

    expect(await repository.findById(created.id)).toEqual(created);
    expect(await repository.findById('missing')).toBeUndefined();
  });

  it('updates an existing note and keeps its id', async () => {
    const created = await repository.create({ title: 'Milk', body: '' });

    const updated = await repository.update(created.id, {
      title: 'Oat milk',
      body: 'One carton',
    });

    expect(updated?.id).toBe(created.id);
    expect(updated?.title).toBe('Oat milk');
    expect(await repository.findAll()).toHaveLength(1);
  });

  it('returns undefined when updating a note that does not exist', async () => {
    const updated = await repository.update('missing', {
      title: 'x',
      body: '',
    });

    expect(updated).toBeUndefined();
  });

  it('deletes a note and reports whether anything was removed', async () => {
    const created = await repository.create({ title: 'Milk', body: '' });

    expect(await repository.delete(created.id)).toBe(true);
    expect(await repository.delete(created.id)).toBe(false);
    expect(await repository.findAll()).toEqual([]);
  });
});

import { describe, expect, it } from 'vitest';
import { InMemoryNoteRepository } from '../../src/repositories/InMemoryNoteRepository';
import { createNoteRepository } from '../../src/repositories/repositoryFactory';

describe('createNoteRepository', () => {

      InMemoryNoteRepository,

  it('gives each caller its own repository', async () => {
    const first = createNoteRepository('memory');

    expect(await second.findAll()).toEqual([]);

Task 5 - Write the first integration tests

Create a folder server/tests/integration, and in it api.test.ts. Notice what beforeEach does. It calls createApp() with a new InMemoryNoteRepository, so every test starts with an application that has never seen a note. Nothing is listening on a port.

Six tests are written. Complete the other six.

  1. Updates a note. Create a note, then put to /api/notes/ plus its id with a new title and body. Expect 200 and a body matching the same id and the new values.
  2. 404 on updating a missing note. put to /api/notes/missing with a valid title.

Task 12 - Evaluate

The server reports over 90 percent coverage. Describe a test suite that would reach the same figure and yet detect almost no defects.

One whose tests call every route and function but assert nothing, or assert only that no exception was thrown. Coverage counts a line as covered when it executes, regardless of whether any expectation depends on its result. A suite like that would keep its coverage figure even if every status code and every response body were wrong.

The unit tests and the integration tests both exercise validation. Is that wasteful duplication? Justify your answer.

They answer different questions. The unit tests cover every rule and boundary of validateNoteInput cheaply, and a failure points straight at that function. The integration tests check that the routes actually call validation and translate its result into a 400 with the right body. Neither can stand in for the other. It would be wasteful only if the integration tests repeated every boundary case, which they do not need to.

The uncovered lines in app.ts include the handler that returns 500 for an unexpected error. Should you write a test to cover it, lower the threshold, or leave it? Argue for one.

A reasonable answer is to test it, because error handling is the code most likely to be wrong and least likely to be exercised by hand. It can be reached by passing createApp a fake repository whose methods throw, which the design already allows. Leaving it is defensible while overall coverage is high, provided the decision is deliberate. Lowering the threshold to hide the gap is the weakest option, because it loosens the rule for every file to excuse one.
