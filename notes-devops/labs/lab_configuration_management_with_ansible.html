Configuration Management with Ansible

Overview

This lab steps away from the Notes pipeline to look at a different problem: keeping long-lived servers configured correctly. You will start two bare servers and a control machine as containers, and use Ansible to turn the bare servers into identical web servers from a description kept in files. You will then run the description again, break a server by hand and repair it, change a setting everywhere at once, and destroy and rebuild the servers from nothing.

Learning Objectives

By the end of this lab you will be able to:

  • Describe the desired state of a group of servers in an Ansible inventory and playbook
  • Explain idempotency and demonstrate it by running a playbook twice
  • Detect and repair configuration drift, previewing changes before applying them
  • Separate configuration data from tasks using variables and templates
  • Evaluate where configuration management fits alongside containers and managed platforms

Concept

Not everything runs in a container on a managed platform. Organisations keep virtual machines, database hosts, network appliances and build servers for years. Configuring one by hand over SSH is manageable. Configuring forty identically is not, and after a few months of urgent fixes nobody can say what is installed where. The gradual, unrecorded divergence of a server from what it is supposed to be is called configuration drift.

Configuration management tools replace hand-typed commands with a description of the desired state: this package is present, this file has this content, this service is running. The tool compares each server with the description and changes only what differs. An operation that can be applied any number of times and leaves the same result is idempotent. That property is what makes it safe to run the same description every day.

Ansible is agentless. A control node connects to each managed node over SSH and needs only Python on the other end. Tools such as Puppet take the other approach, an agent installed on every server that pulls its configuration on a schedule. An inventory lists the servers and groups them. A playbook is a YAML file of tasks, each calling a module such as ansible.builtin.apt or ansible.builtin.template. Ansible configures machines that already exist. Creating the machines is the job of a provisioning tool such as Terraform.

Tasks

Task 1 - Start a branch and define the practice machines

Create an issue named Demonstrate configuration management, move it to In progress, and start a branch.

git switch main
git pull
git switch -c ops/ansible-demo

Create a folder named ansible in the root of the repository, and inside it a folder named target. Create ansible/target/Dockerfile. It stands in for a freshly installed Linux server: an SSH service, Python, a user who may use sudo, and nothing else. No web server is installed.

ansible/target/Dockerfile
# A stand-in for a freshly installed server: SSH, Python, and nothing else.
FROM debian:12-slim

RUN apt-get update \
  && apt-get install -y --no-install-recommends \
    openssh-server python3 python3-apt sudo procps \
  && rm -rf /var/lib/apt/lists/* \
  && mkdir -p /run/sshd \
  && useradd --create-home --shell /bin/bash ansible \
  && echo 'ansible:ansible' | chpasswd \
  && echo 'ansible ALL=(ALL) NOPASSWD:ALL' > /etc/sudoers.d/ansible

EXPOSE 22 80
CMD ["/usr/sbin/sshd", "-D", "-e"]

Create a folder ansible/control and in it a Dockerfile for the control node. Ansible does not run natively on Windows, so it runs in a container that every machine in the class can use.

ansible/control/Dockerfile
FROM python:3.12-slim

RUN apt-get update \
  && apt-get install -y --no-install-recommends openssh-client sshpass \
  && rm -rf /var/lib/apt/lists/* \
  && pip install --no-cache-dir ansible-core

WORKDIR /ansible
CMD ["sleep", "infinity"]

Create ansible/docker-compose.yml. It starts the control node and two servers, web1 and web2, on a private network where they can reach each other by name. The ansible folder is mounted into the control node, so files you edit in Visual Studio Code are immediately visible to Ansible. Each server's web port is published on your machine, on 8181 and 8182.

ansible/docker-compose.yml
services:
  control:
    build: ./control
    container_name: ansible-control
    environment:
      ANSIBLE_CONFIG: /ansible/ansible.cfg
    volumes:
      - .:/ansible

  web1:
    build: ./target
    container_name: web1
    hostname: web1
    ports:
      - '127.0.0.1:8181:80'

  web2:
    build: ./target
    container_name: web2
    hostname: web2
    ports:
      - '127.0.0.1:8182:80'
cd ansible
docker compose up -d --build
docker compose ps

Success condition: three containers are running. http://localhost:8181 in a browser fails to connect, because nothing on web1 is listening for web requests yet.

Task 2 - Tell Ansible which servers exist

Create a folder ansible/inventory, and in it hosts.ini. It defines a group named web containing both servers, and how to log in to them. Read the comment about the password.

ansible/inventory/hosts.ini
[web]
web1
web2

[web:vars]
ansible_user=ansible
# A password in a file is acceptable only because these servers are
# throwaway containers on your own machine. Real inventories use SSH keys.
ansible_password=ansible

Create ansible/ansible.cfg, which tells Ansible where the inventory is.

ansible/ansible.cfg
[defaults]
inventory = inventory/hosts.ini
host_key_checking = False
interpreter_python = /usr/bin/python3

Ask Ansible to contact every server in the group. docker compose exec control runs the rest of the line inside the control node. ping here is an Ansible module that logs in over SSH and checks Python works. It is not a network ping.

docker compose exec control ansible web -m ping

Success condition: both web1 and web2 answer "ping": "pong" with SUCCESS.

Task 3 - Run one command on every server

Ansible can run a single command across a group without a playbook. Ask each server which version of nginx it has.

docker compose exec control ansible web -a "nginx -v"

Success condition: both servers report FAILED, because there is no such program. You have confirmed the starting state of both machines with one line. This is useful for asking questions. It is the wrong tool for making changes, because a command says what to do, not what should be true.

Task 4 - Describe a web server in a playbook

Create a folder ansible/playbooks, and in it site.yml.

  • hosts: web applies the tasks to every server in the group.
  • become: true runs them with sudo.
  • The first task does not say "run apt install". It says the package's state is present. The module works out whether anything needs doing.
  • These practice servers have no service manager, so the last two tasks start nginx directly. The first records whether an nginx process exists and is marked as never changing anything. The second starts nginx only when none was found. Together they describe "nginx is running" in a way that is safe to repeat.
ansible/playbooks/site.yml
- name: Configure the web servers
  hosts: web
  become: true

  tasks:
    - name: Install nginx
      ansible.builtin.apt:
        name: nginx
        state: present
        update_cache: true
        cache_valid_time: 3600

    - name: Check whether nginx is running
      ansible.builtin.command: pgrep -x nginx
      register: nginx_process
      changed_when: false
      failed_when: false

    - name: Start nginx
      ansible.builtin.command: nginx
      when: nginx_process.rc != 0
docker compose exec control ansible-playbook playbooks/site.yml

Success condition: the output lists each task for both servers. The closing PLAY RECAP shows changed=2 and failed=0 for each. http://localhost:8181 and http://localhost:8182 both show the "Welcome to nginx" page.

Task 5 - Run it again

Run exactly the same command a second time.

docker compose exec control ansible-playbook playbooks/site.yml

Success condition: the recap shows changed=0 for both servers, and the Start nginx task says skipping. Nothing was reinstalled and nothing was restarted. The servers already matched the description, so Ansible left them alone. That is idempotency. Imagine the equivalent shell script run twice, and what a second nginx command would do.

Task 6 - Manage a file with a template and a variable

Both servers show the same stock page. Give them a page of your own that states which server produced it. Create a folder ansible/playbooks/templates, and in it index.html.j2. The parts in double curly braces are filled in separately for each server. inventory_hostname is provided by Ansible. site_message is yours to define.

ansible/playbooks/templates/index.html.j2
<!doctype html>
<html lang="en">
  <head>
    <meta charset="utf-8" />
    <title>{{ inventory_hostname }}</title>
  </head>
  <body>
    <h1>{{ site_message }}</h1>
    <p>Served by {{ inventory_hostname }}.</p>
    <p>This file is managed by Ansible. Changes made by hand will be overwritten.</p>
  </body>
</html>

Create a folder ansible/inventory/group_vars, and in it web.yml. A file in group_vars named after a group supplies variables to every server in that group. The data now lives apart from the tasks that use it.

ansible/inventory/group_vars/web.yml
site_message: Hello from the notes team

Open ansible/playbooks/site.yml and add two tasks between Install nginx and Check whether nginx is running. One states that the stock page is absent. The other states that the home page matches the template. The complete playbook is now:

ansible/playbooks/site.yml
- name: Configure the web servers
  hosts: web
  become: true

  tasks:
    - name: Install nginx
      ansible.builtin.apt:
        name: nginx
        state: present
        update_cache: true
        cache_valid_time: 3600

    - name: Remove the page that ships with nginx
      ansible.builtin.file:
        path: /var/www/html/index.nginx-debian.html
        state: absent

    - name: Publish the home page
      ansible.builtin.template:
        src: templates/index.html.j2
        dest: /var/www/html/index.html
        mode: '0644'

    - name: Check whether nginx is running
      ansible.builtin.command: pgrep -x nginx
      register: nginx_process
      changed_when: false
      failed_when: false

    - name: Start nginx
      ansible.builtin.command: nginx
      when: nginx_process.rc != 0
docker compose exec control ansible-playbook playbooks/site.yml

Success condition: the recap shows changed=2 for each server. Only the two new tasks changed anything. Port 8181 shows your message and "Served by web1". Port 8182 shows the same message and "Served by web2". One template produced two different files.

Task 7 - Break a server by hand, then repair it

Play the part of an administrator who logs in to one server late at night and edits a file directly.

docker compose exec web2 sh -c "echo 'Quick fix, will tidy up later' > /var/www/html/index.html"

Reload port 8182. The page is now wrong, and web2 no longer matches web1. This is configuration drift. Before changing anything, ask Ansible what it would do. --check makes no changes, and --diff shows the difference line by line.

docker compose exec control ansible-playbook playbooks/site.yml --check --diff

Success condition: the output shows the hand-written line marked with a minus and the template's lines marked with a plus, for web2 only. The recap reports changed=1 for web2 and changed=0 for web1. Reload port 8182. It is still wrong, because this was a preview.

Now apply it.

docker compose exec control ansible-playbook playbooks/site.yml

Success condition: web2 reports changed=1, web1 reports changed=0, and port 8182 shows the correct page again. Ansible found the one server that had drifted and corrected the one thing that was wrong.

Task 8 - Change a setting everywhere

Open ansible/inventory/group_vars/web.yml and change site_message to a message of your own. Preview the effect, then apply it.

docker compose exec control ansible-playbook playbooks/site.yml --check --diff
docker compose exec control ansible-playbook playbooks/site.yml

Success condition: both servers report changed=1 and both pages show the new message. You edited one line in one file. The number of servers made no difference to the effort.

Task 9 - Destroy the servers and rebuild them

Remove all three containers and start new ones. The new servers are bare again, as if they had just been installed.

docker compose down
docker compose up -d
docker compose exec control ansible web -a "nginx -v"

The last command fails on both, as it did at the start. Now run the playbook once.

docker compose exec control ansible-playbook playbooks/site.yml

Success condition: one command, and both servers are back exactly as they were, including your message. Everything that defines them is in files in your repository. The servers themselves have become disposable.

Task 11 - Evaluate

The Notes product is deployed as a container image to a managed platform. What, if anything, would Ansible add to that pipeline? Be honest about the answer.

Very little. The image already fixes what is installed and how it is configured, and it is replaced, not modified, on each release, so there is no long-lived server to drift. The platform runs it. Ansible earns its place where machines persist and must be kept in a known state: virtual machines, self-hosted CI servers such as a Jenkins controller, database hosts, or the container hosts themselves if you run your own. Adding it to this pipeline for its own sake would be complexity without benefit.

Ansible pushes configuration from a control node over SSH. Puppet uses an agent on each server that pulls configuration on a schedule. Give one consequence of each design.

Push and agentless: nothing to install or keep running on the managed servers, and changes happen when you choose. But nothing corrects drift between runs unless you schedule runs yourself, and the control node needs network access and credentials for every server. Pull with an agent: every server corrects its own drift continuously and new servers configure themselves on first contact. But the agent is one more piece of software to deploy, secure and upgrade on every machine, and a central server must be kept available.

In Task 7 the hand-made change was overwritten without warning. Is that the behaviour you want? What process would have to exist around the tool for it to be safe?

It is the behaviour that keeps servers consistent, and it is also a way to destroy a legitimate emergency fix. It is safe only if the repository is the single agreed source of truth: every change, including urgent ones, is made in the playbook and reviewed, people know that manual edits will not survive, check mode with diff is run and read before applying, and playbook runs are logged. Without that agreement the tool and the administrators will keep undoing each other.
