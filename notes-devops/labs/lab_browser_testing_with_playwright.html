Browser Testing with Playwright

Overview

This lab tests the Notes product the way a user meets it: a real browser, loading the real built front end, talking to the real API. You will use Playwright to drive Chromium through creating, editing and deleting a note, and then add an automated accessibility scan of the page. These are the first tests in the project in which nothing is mocked.

Learning Objectives

By the end of this lab you will be able to:

  • Configure Playwright to start the built application and run tests against it
  • Write end-to-end tests that follow a user story from the first click to the visible result
  • Design tests that stay independent while sharing one running server
  • Add automated accessibility checks and explain which problems they can and cannot detect
  • Compare the cost and the confidence of end-to-end tests with the lower layers of tests

Concept

The component tests in the React Front End and Component Tests lab mock the API. The integration tests in the Back End Tests and Coverage Gates lab never load a page. Each half is tested against an assumption about the other half. If the front end sends a field the back end does not expect, both suites pass and the product is broken.

An end-to-end test removes the assumption by running everything together. Playwright launches a real browser without a visible window, called headless mode, and controls it from a test. A locator such as page.getByRole('button', { name: 'Add note' }) describes how to find an element. Playwright waits for it to be ready before acting, and expect(locator).toBeVisible() keeps retrying until it is true or a timeout passes. That auto-waiting is what keeps browser tests from failing at random when a page is slow. The webServer setting starts the application before the tests and stops it afterwards.

The price is speed and precision. These tests take seconds each, and a failure says "the user could not do this" without saying which layer is at fault. An accessibility scan with axe inspects the rendered page against the WCAG guidelines, catching problems such as poor colour contrast or a field with no label. It finds only what a program can detect, which is a minority of real accessibility barriers.

Task 2 - Configure Playwright to start the application

Create e2e/playwright.config.ts. Read the webServer section closely.

  • command and cwd run npm start in the server folder. That runs the compiled server, not the development one.
  • env sets PUBLIC_DIR to the built front end. The server from the Notes API and the Repository Pattern lab serves a folder of static files when it is given one, so one process now provides both the page and the API on port 3000. There is no Vite and no proxy.
  • url is the address Playwright polls until the server answers, before it starts any test.
  • If BASE_URL is set, none of this happens, and the tests run against whatever is at that address instead.
e2e/playwright.config.ts
import { defineConfig, devices } from '@playwright/test';

// Set BASE_URL to test an app that is already running somewhere else.
// Without it, Playwright starts the built app itself on port 3000.
const externalUrl = process.env.BASE_URL;

export default defineConfig({
  testDir: './tests',
  forbidOnly: !!process.env.CI,
  retries: process.env.CI ? 1 : 0,
  reporter: [['list'], ['html', { open: 'never' }]],
  use: {
    baseURL: externalUrl ?? 'http://localhost:3000',
    trace: 'on-first-retry',
    screenshot: 'only-on-failure',
  },
  projects: [{ name: 'chromium', use: { ...devices['Desktop Chrome'] } }],
  webServer: externalUrl
    ? undefined
    : {
        command: 'npm start',
        cwd: '../server',
        url: 'http://localhost:3000/api/health',
        reuseExistingServer: !process.env.CI,
        env: { PUBLIC_DIR: '../client/dist' },
      },
});

The configuration runs built code, so build both halves first. Repeat these two builds whenever you change application code and want the browser tests to see it.

npm run build --prefix ../client
npm run build --prefix ../server

Task 3 - Write the first browser test

Create a folder e2e/tests, and in it notes.spec.ts with the content below. Two things in it are responses to a real constraint. Every test in this file talks to the same running server, and that server keeps every note it is given.

  • unique() adds a random suffix to each title, so a test only ever looks for a note that it alone created.
  • addNote() waits for the new heading to be visible before it returns, so the next step never races the page.
e2e/tests/notes.spec.ts
import { randomUUID } from 'node:crypto';
import { expect, test } from '@playwright/test';
import type { Page } from '@playwright/test';

// Every test shares one running server, so each one uses a title nobody
// else will create.
function unique(label: string): string {
  return `${label} ${randomUUID().slice(0, 8)}`;
}

async function addNote(page: Page, title: string, body = '') {
  await page.getByLabel('Title').fill(title);
  await page.getByLabel('Body').fill(body);
  await page.getByRole('button', { name: 'Add note' }).click();
  await expect(page.getByRole('heading', { name: title })).toBeVisible();
}

test.beforeEach(async ({ page }) => {
  await page.goto('/');
});

test('a user can create a note', async ({ page }) => {
  const title = unique('Shopping');

  await addNote(page, title, 'Milk and bread');

  await expect(page.getByText('Milk and bread').first()).toBeVisible();
  await expect(page.getByLabel('Title')).toHaveValue('');
});
npx playwright test

Success condition: Playwright starts the server, runs 1 test in Chromium, and reports 1 passed. Nothing appears on screen, because the browser is headless.

Task 6 - Scan the page for accessibility violations

Create e2e/tests/accessibility.spec.ts. AxeBuilder analyses whatever the page looks like at that moment, so each test first puts the page into a state worth checking: one with a note in the list, and one showing the validation error. The tags limit the scan to WCAG 2.1 levels A and AA, the standard public sector websites in the UK are required to meet.

e2e/tests/accessibility.spec.ts
import AxeBuilder from '@axe-core/playwright';
import { expect, test } from '@playwright/test';
import type { Page } from '@playwright/test';

const WCAG_TAGS = ['wcag2a', 'wcag2aa', 'wcag21a', 'wcag21aa'];

async function scan(page: Page) {
  const results = await new AxeBuilder({ page }).withTags(WCAG_TAGS).analyze();
  return results.violations;
}

test('the page has no detectable accessibility violations', async ({
  page,
}) => {
  await page.goto('/');
  await page.getByLabel('Title').fill('Accessibility check');
  await page.getByRole('button', { name: 'Add note' }).click();
  await expect(
    page.getByRole('heading', { name: 'Accessibility check' }).first(),
  ).toBeVisible();

  expect(await scan(page)).toEqual([]);
});

test('the validation error state has no detectable violations', async ({
  page,
}) => {
  await page.goto('/');
  await page.getByRole('button', { name: 'Add note' }).click();
  await expect(page.getByRole('alert')).toBeVisible();

  expect(await scan(page)).toEqual([]);
});
npx playwright test

Success condition: 7 passed. The scan found nothing it can detect on either state of the page.

Task 9 - Evaluate

You now have unit, component, integration and end-to-end tests. If the team could keep only two of the four layers, which would you keep and why?

There is no single right answer, but a strong one weighs speed and precision against realism. Keeping unit tests and end-to-end tests gives fast, precise feedback on logic plus proof that the assembled product works, at the cost of slow diagnosis when an end-to-end test fails. Keeping integration and end-to-end tests proves the API contract and the user journeys but leaves edge cases of the logic expensive to cover. A good answer names what is lost as well as what is kept.

The accessibility tests pass. Give two accessibility problems the Notes page could still have that an automated scan cannot detect.

Examples: the order in which focus moves with the Tab key may be illogical, a screen reader user may not be told that a note was added or deleted because nothing announces the change, link or button wording may be technically present but meaningless, or the page may be unusable at 400 percent zoom. Automated tools detect only a minority of WCAG failures. The rest need testing with a keyboard, a screen reader and real users.

The tests avoid depending on an empty list by using unique titles. What is the alternative design, and what would it cost?

The alternative is to reset the server state before each test, for example through a test-only endpoint that clears the store, or by starting a fresh server per test. Tests could then assert on exact list contents. The costs are a reset mechanism that must never be reachable in production, slower tests if a server is started each time, and the loss of safe parallel execution against one shared server.
