ACCA7023 - Agile and DevOps

Agile Setup and Git Workflow

Overview

This lab sets up the working agreement for a small product called Notes, before any of it is built. You will create the repository, write the backlog as user stories with acceptance criteria, arrange those stories on a board and a story map, and lock the main branch so that every change has to arrive through a pull request. You finish by delivering your first change through that route, which proves the rules work.

Learning Objectives

By the end of this lab you will be able to:

  • Write user stories with acceptance criteria that can be checked by a test
  • Arrange a backlog on a board and a story map, and choose a first release from it
  • Protect a main branch so that changes can only arrive through a reviewed pull request
  • Deliver a change using a short-lived branch, a pull request linked to its story, and a merge

Concept

A team that commits straight to its main branch has no moment at which anybody, or anything, checks a change before it becomes the product. Problems are found after the fact, by whoever pulls next. A team that keeps its plan in people's heads has a second problem. Nobody can say what "done" means for a piece of work, so nobody can say whether a test proves it.

Scrum answers the planning problem with a product backlog of user stories. A story names who wants something and why, in the form "As a, I can, so that". Its acceptance criteria state what must be observably true for the story to be finished, often written as "Given, when, then". A story map arranges stories left to right along the user's journey, with a line under the first release, so the team can see what the smallest useful product is.

GitHub Flow answers the change problem. The main branch always holds releasable work. Each story is built on a short-lived branch, offered back through a pull request, checked, and merged. A ruleset on main makes that route the only route. You will use GitHub Issues for stories, GitHub Projects for the board, and git switch, git push and the pull request page for the flow.

Tasks

Task 1 - Create and clone the repository

  1. Sign in to GitHub and create a new repository named notes-devops.
  2. Set it to Public. Public repositories receive free pipeline minutes and free package hosting, which the rest of this practical relies on.
  3. Tick Add a README file, then create the repository.
  4. Clone it to your machine and open the folder in Visual Studio Code. Replace YOUR-USER with your GitHub user name.
git clone https://github.com/YOUR-USER/notes-devops.git
cd notes-devops
code .

Task 2 - Add the housekeeping files

Three small files stop common problems before they start. Create each one in the root of the repository with the content shown.

Create .gitignore. It keeps downloaded packages, build output and test reports out of version control.

.gitignore
node_modules/
dist/
coverage/
server/public/
playwright-report/
test-results/
.env
*.log

Create .gitattributes. Windows and Linux end lines of text differently. This file tells Git to store and check out every text file with Linux line endings, so a file never looks changed just because of the machine it was edited on.

.gitattributes
* text=auto eol=lf

Create .prettierrc.json. It records the one formatting choice the project makes, so every tool and every person formats code the same way.

.prettierrc.json
{
  "singleQuote": true
}

Commit the three files and push them. This is the last time you will push directly to main.

git add .gitignore .gitattributes .prettierrc.json
git commit -m "Add housekeeping files"
git push

Task 3 - Write the backlog as issues

Each user story becomes one GitHub issue. In your repository open Issues, create a label named story, then create the five issues below. Put the story sentence and the acceptance criteria in the issue description, and apply the story label.

  1. Create a note. As a user, I can create a note with a title and body, so that I do not have to remember it.
  2. List my notes. As a user, I can see a list of my notes, so that I can find what I wrote.
  3. Edit a note. As a user, I can edit a note, so that I can correct or extend it.
  4. Delete a note. As a user, I can delete a note, so that the list only holds what I still need.
  5. Health endpoint. As an operator, I can call a health endpoint, so that I can tell whether the service is alive and which version is running.

Write at least two acceptance criteria for each story yourself. A good criterion describes something a person or a test could check and get a yes or no answer. Here is the set for the first story as a model.

  • Given the form is empty, when I enter a title and press Add note, then the note appears in the list.
  • Given the title is empty, when I press Add note, then I am told a title is required and nothing is saved.
  • A title longer than 100 characters is refused.

Add two more issues for stories that are not in the first release: Search notes and Pin a note. Write the story sentence for each. They give the backlog something to prioritise against.

Task 4 - Build the board

  1. Open the Projects tab of your repository and create a new project using the Board layout. Name it Notes.
  2. Give the board five columns, in this order: Backlog, Ready, In progress, In review, Done.
  3. Add all seven issues to the project. They start in Backlog.
  4. Move the five first-release stories to Ready. That column is your first sprint. Search and Pin stay in Backlog.
  5. Order the Ready column from top to bottom in the order you would build the stories. Think about which stories cannot be demonstrated until another one exists.

Success condition: the board shows five stories in Ready, in a deliberate order, and two in Backlog.

Task 5 - Protect the main branch

  1. In the repository open Settings, then Rules, then Rulesets, and create a new branch ruleset named protect-main.
  2. Set Enforcement status to Active.
  3. Under Target branches add the default branch.
  4. Leave the Bypass list empty. An owner who can bypass the rule is not protected by it.
  5. Turn on Restrict deletions, Require a pull request before merging and Block force pushes.
  6. Leave the number of required approvals at zero. You are working alone, and GitHub does not let you approve your own pull request. The pull request still gives every change a recorded checkpoint.
  7. Save the ruleset.

Task 6 - Prove that main refuses a direct push

A rule that has never been seen to refuse anything cannot be trusted. Make a harmless change on main and try to push it.

echo "Notes application for the DevOps practical." >> README.md
git commit -am "Describe the project"
git push

Success condition: the push is rejected, and the message says that changes must be made through a pull request.

The commit still exists on your machine. Undo it so that your local main matches GitHub again.

git reset --hard origin/main

Task 7 - Deliver the story map through a pull request

Now make a change the permitted way. The change is the story map itself, kept in the repository so that it is versioned alongside the code it describes.

  1. On the board, create a new issue named Record the story map and move it to In progress. Note its issue number.
  2. Create a branch for it.
git switch -c docs/story-map

Create a folder named docs, and in it a file named user-stories.md. Start from the content below, then replace the acceptance criteria with the ones you wrote in your issues where yours differ.

docs/user-stories.md
# Notes: user stories and story map

## Story map

The top row is the journey a user takes, left to right. Stories sit under the
activity they belong to. Everything above the release line is needed before
the product is worth showing to anybody.

| Capture       | Review        | Maintain       | Operate         |
| ------------- | ------------- | -------------- | --------------- |
| Create a note | List my notes | Edit a note    | Health endpoint |
|               |               | Delete a note  |                 |
| **Release 1** | **Release 1** | **Release 1**  | **Release 1**   |
|               | Search notes  | Pin a note     |                 |

## Stories

### 1. Create a note

As a user, I can create a note with a title and body, so that I do not have
to remember it.

Acceptance criteria:

- Given the form is empty, when I enter a title and press Add note, then the
  note appears in the list.
- Given the title is empty, when I press Add note, then I am told a title is
  required and nothing is saved.
- A title longer than 100 characters is refused.

### 2. List my notes

As a user, I can see a list of my notes, so that I can find what I wrote.

Acceptance criteria:

- Given notes exist, when I open the page, then every note's title and body
  is shown.
- Given no notes exist, when I open the page, then I am told there are none yet.

### 3. Edit a note

As a user, I can edit a note, so that I can correct or extend it.

Acceptance criteria:

- Given a note exists, when I choose Edit, change the title and save, then the
  list shows the new title and not the old one.
- Given I am editing, when I choose Cancel, then the note is unchanged.

### 4. Delete a note

As a user, I can delete a note, so that the list only holds what I still need.

Acceptance criteria:

- Given a note exists, when I choose Delete, then it is no longer in the list.

### 5. Health endpoint

As an operator, I can call a health endpoint, so that I can tell whether the
service is alive and which version is running.

Acceptance criteria:

- `GET /api/health` returns status 200 with `status` equal to `ok`.
- The response includes the version of the running build.

Commit the file and push the branch. The first push of a new branch needs to be told where to go.

git add docs/user-stories.md
git commit -m "Record the story map and acceptance criteria"
git push -u origin docs/story-map
  1. Open the repository on GitHub. It offers to create a pull request from the branch you just pushed. Accept.
  2. In the description write Closes #N, replacing N with the issue number. This links the pull request to the story.
  3. Create the pull request and move the card to In review.
  4. Read the Files changed tab as if somebody else had written it. Then choose Squash and merge, and delete the branch when GitHub offers.
  5. Bring your machine back in line.
git switch main
git pull
git branch -d docs/story-map

Success condition: docs/user-stories.md is on main, the issue closed itself when the pull request merged, and its card is in Done.

Task 8 - Evaluate

The ruleset requires a pull request but zero approvals. What does that still give a developer working alone, and what does it not give?

It gives a recorded checkpoint for every change: a diff that can be read before merging, a link back to the story, a place for automated checks to report, and a history of what was merged and why. It does not give independent review. Nobody other than the author has looked at the change, so mistakes the author is blind to pass straight through.

Pick one of your acceptance criteria and say what kind of automated test could check it. Then pick one that would be hard to automate and say why.

A criterion such as "a title longer than 100 characters is refused" maps directly onto a unit test of a validation function or an API test expecting status 400. A criterion that depends on judgement, such as "the page is easy to use", has no yes or no answer a program can compute, so it needs rewording into something observable or checking by a person.

Why does the story map draw a release line, instead of simply listing the stories in priority order?

A priority list says what to build next but not when the product becomes useful. The release line shows the smallest set of stories that covers the whole journey from left to right. It makes it visible when a team is polishing one activity while another has nothing at all.
