ACCA7023 - Agile and DevOps

Containerising the Application

Overview

This lab packages the whole Notes product, front end and back end together, into one container image that runs the same way on any machine with Docker. You will write a multi-stage Dockerfile, run the image locally, point the browser tests from the Browser Testing with Playwright lab at the running container, and scan the image for known vulnerabilities. The scan leads to a change that makes the image safer by removing something from it.

Learning Objectives

By the end of this lab you will be able to:

  • Write a multi-stage Dockerfile that separates build tools from the image that ships
  • Build, run and inspect a container locally
  • Explain why a container that keeps state in memory loses it when replaced
  • Scan an image for known vulnerabilities and act on the findings
  • Evaluate the trade-off of shipping the front end and back end in a single image

Concept

The application runs on your machine because your machine has the right version of Node.js, the right packages, and two build steps performed in the right order. "It works on my machine" is the problem. Any other machine, including the server that will eventually host the product, has to be given the same set-up by hand, and any difference is a defect waiting to be discovered in production.

A container image is a file-system snapshot holding an application together with everything it needs to run. A container is a running, isolated process started from an image. A Dockerfile is the recipe for an image. Each instruction adds a layer, and Docker reuses unchanged layers from its cache, which is why the order of instructions affects build speed.

Building this application needs a compiler, a bundler and several hundred development packages. Running it needs none of them. A multi-stage build uses several FROM instructions in one Dockerfile. Early stages do the building. The final stage starts from a clean base and uses COPY --from= to take only the finished output. Everything else is discarded. The fewer programs an image contains, the smaller its attack surface, which is the set of things that could contain an exploitable flaw. A vulnerability scanner such as Trivy lists the packages in an image and compares them against databases of known vulnerabilities.

Tasks

Task 1 - Start a branch and decide what Docker may see

You need Docker Desktop running. Create an issue named Package the application as a container, move it to In progress, and start a branch.

git switch main
git pull
git switch -c build/container-image

Create .dockerignore in the root of the repository. When Docker builds, it first sends the whole folder to the build engine. This file lists what to leave behind: packages that will be installed fresh inside the image, output from local builds, and files the image has no use for. Without it a build is slower, and local leftovers can leak into the image.

.dockerignore
.git
**/node_modules
**/dist
**/coverage
**/playwright-report
**/test-results
e2e
docs
*.md

Task 2 - Write the build stages

Create a file named Dockerfile, with no extension, in the root of the repository. Start with the two stages that build the two halves.

In each stage the package*.json files are copied and npm ci is run before the source code is copied. Dependencies change rarely and source changes constantly. Ordered this way, Docker reuses the cached dependency layer on every build where only source code changed. npm ci installs exactly what package-lock.json records and fails if the two files disagree, which is what you want from an automated build.

Dockerfile
# Stage 1 - build the React front end into static files
FROM node:22-alpine AS client-build
WORKDIR /app/client
COPY client/package*.json ./
RUN npm ci
COPY client/ ./
RUN npm run build

# Stage 2 - compile the Express back end from TypeScript to JavaScript
FROM node:22-alpine AS server-build
WORKDIR /app/server
COPY server/package*.json ./
RUN npm ci
COPY server/ ./
RUN npm run build

Task 3 - Write the stage that ships

Add a third stage to the end of the Dockerfile. It has no AS name because it is the result. Complete each TODO.

  1. Copy server/package*.json into the working folder and run npm ci --omit=dev, which installs only the packages listed under dependencies. Follow it with npm cache clean --force in the same RUN, joined by &&, so the download cache is not kept in the layer.
  2. Copy the compiled server from the server-build stage, /app/server/dist, to ./dist.
  3. Copy the built front end from the client-build stage, /app/client/dist, to ./public. That is the folder name the server looks for by default.
  4. Switch to the unprivileged user named node, which the base image already provides.
  5. Set the command to node dist/server.js, written as a JSON array.
Dockerfile
# Stage 3 - the image that actually ships
FROM node:22-alpine
ENV NODE_ENV=production
WORKDIR /app

# Production dependencies only. No compiler, no test tools.
# TODO: COPY the server package files
# TODO: RUN npm ci --omit=dev and clean the npm cache

# TODO: COPY --from=server-build the compiled server to ./dist
# TODO: COPY --from=client-build the built front end to ./public

ARG APP_VERSION=dev
ENV APP_VERSION=$APP_VERSION
ENV PORT=3000
EXPOSE 3000

# Do not run the application as root.
# TODO: USER

HEALTHCHECK --interval=30s --timeout=3s --retries=3 \
  CMD wget -qO- http://localhost:3000/api/health || exit 1

# TODO: CMD

ARG APP_VERSION is a value supplied when the image is built. Copying it into an ENV makes it visible to the running application, where config.ts reads it. The image will know which build it is.

Task 4 - Build and run the image

Build the image from the root of the repository. The final . is the folder to build from. The first build downloads the base image and installs every package, so it takes a few minutes.

docker build --build-arg APP_VERSION=local -t notes-devops:local .

Make sure nothing else is using port 3000, then start a container from the image. -d runs it in the background and -p connects port 3000 on your machine to port 3000 inside the container.

docker run -d --name notes -p 3000:3000 notes-devops:local
curl -s http://localhost:3000/api/health

Success condition: the health check answers with "version":"local", and http://localhost:3000 in a browser shows the Notes page, fully working. Neither Node.js nor the project's packages on your own machine were involved. Everything came from the image.

Task 5 - Look inside the container

docker exec notes whoami
docker exec notes ls /app
docker exec notes ls /app/dist
docker image ls notes-devops:local

Success condition: the user is node, not root. /app holds dist, public, node_modules and the package files. There is no src folder, no TypeScript, no tests. The compiler that produced dist was left behind in a stage that no longer exists.

Task 6 - Replace the container and see what is lost

Add two or three notes through the page. Then remove the container and start a new one from the same image.

docker rm -f notes
docker run -d --name notes -p 3000:3000 notes-devops:local

Success condition: reload the page. The notes are gone. The image is unchanged, but the notes were never in the image. They were in the memory of a process that no longer exists. Any platform that replaces containers, to deploy a new version or to recover from a crash, will do exactly this to the product as it stands.

Task 7 - Run the browser tests against the container

The Playwright configuration skips starting its own server when BASE_URL is set. Use that to test the container, which is the real artefact, instead of a local build.

cd e2e
BASE_URL=http://localhost:3000 npx playwright test
cd ..

Success condition: 7 passed. The same tests that proved the code now prove the packaged product.

Task 8 - Scan the image

Trivy is itself distributed as a container image, so there is nothing to install. The command gives it access to Docker, so that it can read your local image, and asks for HIGH and CRITICAL findings that already have a fix available. --exit-code 1 makes the command fail if it finds any.

MSYS_NO_PATHCONV=1 docker run --rm \
  -v /var/run/docker.sock:/var/run/docker.sock \
  ghcr.io/aquasecurity/trivy:latest image \
  --severity HIGH,CRITICAL --ignore-unfixed --exit-code 1 \
  notes-devops:local
echo "exit code: $?"

Read the report. It is grouped by where in the image each package was found. Results change from week to week as new vulnerabilities are published and base images are patched, so yours will not match anybody else's exactly.

Look at the path of anything reported. When this lab was written, every finding was in packages such as pacote and sigstore, under usr/local/lib/node_modules/npm. Those are not dependencies of the Notes application. They are parts of npm itself, which the base image includes. Express and its dependencies under app/node_modules were clean.

Task 9 - Remove what the running application does not need

The final stage uses npm once, to install production dependencies. After that the running application never calls it. Whether or not your scan reported anything in it today, it is software in the image that can only ever be a liability.

Open the Dockerfile and extend the RUN instruction in the final stage so that it deletes npm after using it. It must be the same RUN. A file deleted in a later instruction is hidden but still present in the earlier layer.

Dockerfile
# npm is removed afterwards because the running app never needs it, and
# every package left in the image is one more thing to patch.
COPY server/package*.json ./
RUN npm ci --omit=dev \
  && npm cache clean --force \
  && rm -rf /usr/local/lib/node_modules/npm /usr/local/bin/npm /usr/local/bin/npx

Rebuild, replace the container, and repeat the scan from the previous task.

docker build --build-arg APP_VERSION=local -t notes-devops:local .
docker rm -f notes
docker run -d --name notes -p 3000:3000 notes-devops:local
curl -s http://localhost:3000/api/health

Success condition: the application still answers, and the scan no longer lists anything under usr/local/lib/node_modules/npm. When this lab was written the scan then reported no HIGH or CRITICAL findings at all and exited with code 0. If yours reports findings in the base operating system or in Express, record them in an issue. Deciding what to do about a finding you cannot remove is part of the job.

Task 10 - Audit the dependencies and merge

The image scan looked at what was installed. npm audit asks the same question of the dependency list itself, and it is much faster. Run it for both halves.

npm audit --omit=dev --audit-level=high --prefix server
npm audit --omit=dev --audit-level=high --prefix client

Stop the container, then commit, push, and merge through a pull request that closes the issue.

docker rm -f notes
git add .
git commit -m "Add multi-stage Dockerfile"
git push -u origin build/container-image

Task 11 - Evaluate

The front end and back end ship in one image. Give one advantage of that decision and one situation in which it would become the wrong decision.

Advantage: one artefact to build, scan, version and deploy, with no cross-origin configuration and no risk of a front end running against a mismatched back end. It becomes the wrong decision when the two halves need to change or scale independently: for example a front end released many times a day against a slow-moving API, static files that would be better served from a content delivery network, or several teams each owning one half.

A scan reports a HIGH vulnerability in a package the application never calls. A colleague says it can be ignored. What would you want to know before agreeing?

Whether the vulnerable code is reachable at all in the running container, by the application or by an attacker who has gained a foothold. Whether the package can simply be removed, which is better than arguing about it. Whether a fixed version exists. And whether any policy or customer requires a clean scan regardless of reachability. An unreachable finding may be a low real risk, but it is still noise that can hide a finding that matters.

Why does the lost-notes behaviour in Task 6 matter more for a container platform than it did when you ran the server from a terminal?

On a developer machine the process is restarted rarely and by the person using it. A container platform replaces containers as a matter of routine: on every deployment, when it scales in or out, when a host is maintained, or after a crash. With more than one replica, each would also hold a different set of notes. In-memory state turns from an occasional inconvenience into data loss on every release, so real persistence has to live outside the container.
