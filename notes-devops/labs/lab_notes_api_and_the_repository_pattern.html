Notes API and the Repository Pattern

Overview

This lab builds the back end of the Notes product: a small REST API written in TypeScript with Express. It can create, list, edit and delete notes, and report its own health. The API is deliberately small. What matters is how it is put together. Storage sits behind an interface, a factory decides which storage to build, and configuration is read once in one place. Those three choices are what make the code easy to test and safe to change.

Learning Objectives

By the end of this lab you will be able to:

  • Explain how a repository interface lowers the coupling between request handling and storage
  • Implement a Factory function that is the only code naming a concrete repository class
  • Explain why a configuration module behaves as a Singleton and what that guarantees
  • Implement REST handlers that choose correct status codes for success, invalid input and missing resources
  • Run and exercise an Express API locally from the command line

Concept

The quickest way to write a notes API is to keep an array inside the route file and have every handler read and write it directly. It works, and it is hard to live with. The handlers cannot be tested without the array, the array cannot be swapped for a database without rewriting every handler, and a rule such as "titles are required" ends up copied into each route that accepts a note.

Coupling is how much one part of a program has to know about another. Cohesion is how closely the things inside one part belong together. The design in this lab lowers the first and raises the second. A repository is an object whose only job is storing and finding notes. The routes depend on a NoteRepository interface, a list of method signatures with no implementation, so they work with any class that provides those methods.

Something still has to choose a concrete class. The Factory pattern puts that choice in one function, createNoteRepository(storeType). The Singleton pattern guarantees one shared instance of something. In Node.js a module is evaluated once and then cached, so an object exported from config.ts is the same object in every file that imports it. You will use express.Router() to group routes, express.json() to parse request bodies, and res.status() to set response codes.

Task 2 - Read configuration once

Create a folder server/src, and in it config.ts. This is the only file in the back end that reads environment variables. Every other file imports the config object. Object.freeze stops any of them changing it.

server/src/config.ts
import path from 'node:path';

export interface AppConfig {
  port: number;
  storeType: string;
  publicDir: string;
  version: string;
}

function loadConfig(): AppConfig {
  return {
    port: Number(process.env.PORT ?? 3000),
    storeType: process.env.STORE_TYPE ?? 'memory',
    publicDir: path.resolve(process.env.PUBLIC_DIR ?? 'public'),
    version: process.env.APP_VERSION ?? 'dev',
  };
}

// Node caches a module after its first import, so every file that imports
// config receives this same frozen object. The environment is read once.
export const config: AppConfig = Object.freeze(loadConfig());

Task 3 - Define what a repository must do

Create a folder server/src/repositories, and in it NoteRepository.ts. It contains no behaviour at all, only shapes. Every method returns a Promise so that a store which has to wait for a database could implement the same interface.

server/src/repositories/NoteRepository.ts
export interface Note {
  id: string;
  title: string;
  body: string;
  createdAt: string;
  updatedAt: string;
}

export interface NoteInput {
  title: string;
  body: string;
}

// The routes depend on this interface only. They never name a concrete store.
export interface NoteRepository {
  findAll(): Promise<Note[]>;
  findById(id: string): Promise<Note | undefined>;
  create(input: NoteInput): Promise<Note>;
  update(id: string, input: NoteInput): Promise<Note | undefined>;
  delete(id: string): Promise<boolean>;
}

Task 6 - Keep the rules in one place

Create server/src/validation.ts. It decides whether a request body is an acceptable note. It knows nothing about HTTP and nothing about storage, which is what makes it cohesive. It returns either the cleaned-up note or the complete list of problems, never a mixture.

server/src/validation.ts
import type { NoteInput } from './repositories/NoteRepository';

export const MAX_TITLE_LENGTH = 100;
export const MAX_BODY_LENGTH = 2000;

export type ValidationResult =
  { ok: true; value: NoteInput } | { ok: false; errors: string[] };

export function validateNoteInput(payload: unknown): ValidationResult {
  const errors: string[] = [];
  const data = (payload ?? {}) as Record<string, unknown>;

  const title = typeof data.title === 'string' ? data.title.trim() : '';
  if (title.length === 0) {
    errors.push('Title is required');
  } else if (title.length > MAX_TITLE_LENGTH) {
    errors.push(`Title must be ${MAX_TITLE_LENGTH} characters or fewer`);
  }

  let body = '';
  if (data.body !== undefined) {
    if (typeof data.body !== 'string') {
      errors.push('Body must be text');
    } else if (data.body.length > MAX_BODY_LENGTH) {
      errors.push(`Body must be ${MAX_BODY_LENGTH} characters or fewer`);
    } else {
      body = data.body.trim();
    }
  }

  if (errors.length > 0) {
    return { ok: false, errors };
  }
  return { ok: true, value: { title, body } };
}

import { Router } from 'express';

export function createHealthRouter(): Router {
  const router = Router();

  router.get('/', (_req, res) => {
    res.json({
      status: 'ok',
      version: config.version,
      uptimeSeconds: Math.round(process.uptime()),

Task 8 - Implement the notes routes

Create server/src/routes/notes.ts. The router receives its repository as an argument and never imports a concrete one. GET and POST are written for you. Complete PUT and DELETE.

  1. PUT /:id validates the body exactly as POST does, and answers 400 with the errors if it is invalid.
  2. It then calls repository.update() with req.params.id. If that returns nothing, answer 404 with { errors: ['Note not found'] }. Otherwise answer with the updated note.
  3. DELETE /:id calls repository.delete(). If nothing was deleted, answer 404 in the same shape. Otherwise answer 204 with no body, using res.status(204).end().
server/src/routes/notes.ts
import { Router } from 'express';
import type { NoteRepository } from '../repositories/NoteRepository';
import { validateNoteInput } from '../validation';

// Each handler does three things only: read the request, call the
// repository, and choose a status code. The rules live elsewhere.
export function createNotesRouter(repository: NoteRepository): Router {
  const router = Router();

  router.get('/', async (_req, res) => {
    res.json(await repository.findAll());
  });

  router.post('/', async (req, res) => {
    const result = validateNoteInput(req.body);
    if (!result.ok) {
      res.status(400).json({ errors: result.errors });
      return;
    }
    const note = await repository.create(result.value);
    res.status(201).json(note);
  });

Task 9 - Assemble the application

Create server/src/app.ts. createApp() builds the Express application from a repository it is handed. It mounts the two routers, answers unknown /api paths with a JSON 404, serves a folder of static files if one exists at the path it is given, and turns malformed JSON into a 400. It does not start listening. That separation is deliberate. An application object that is not attached to a network port can be created as many times as you like.

server/src/app.ts
import fs from 'node:fs';
import path from 'node:path';
import express from 'express';
import type { ErrorRequestHandler, Express } from 'express';
import type { NoteRepository } from './repositories/NoteRepository';
import { createHealthRouter } from './routes/health';
import { createNotesRouter } from './routes/notes';

// The repository is passed in, so a test can hand the app a fresh store
// and production can hand it whatever the factory built.
export function createApp(
  repository: NoteRepository,
  publicDir?: string,
): Express {
  const app = express();
  app.disable('x-powered-by');
  app.use(express.json());

  app.use('/api/health', createHealthRouter());
  app.use('/api/notes', createNotesRouter(repository));

  app.use('/api', (_req, res) => {
    res.status(404).json({ errors: ['Not found'] });
  });

  // In production the built front end is served from the same process.
  if (publicDir && fs.existsSync(publicDir)) {
    app.use(express.static(publicDir));
    app.use((_req, res) => {
      res.sendFile(path.join(publicDir, 'index.html'));
    });
  }

  const errorHandler: ErrorRequestHandler = (err, _req, res, _next) => {
    if (err instanceof SyntaxError) {
      res.status(400).json({ errors: ['Request body is not valid JSON'] });
      return;
    }
    console.error(err);
    res.status(500).json({ errors: ['Internal server error'] });
  };
  app.use(errorHandler);

  return app;
}

  -H "Content-Type: application/json" \
  -d '{"title":"Oat milk","body":"One carton"}'

curl -i -X POST http://localhost:3000/api/notes \
  -H "Content-Type: application/json" \
  -d '{"body":"No title"}'

# Delete the note, then try to delete it again
curl -i -X DELETE http://localhost:3000/api/notes/ID
curl -i -X DELETE http://localhost:3000/api/notes/ID

Success condition: health answers {"status":"ok","version":"dev",...}. Creating answers with the note and an id. Updating answers with the new title and the same id. The note with no title gets 400 and Title is required. The first delete gets 204 and the second gets 404.

Stop the server with Ctrl+C, start it again, and list the notes. The list is empty. The notes lived in the memory of the process you stopped. Keep that limitation in mind. It is a known one, not a defect.

Task 12 - Evaluate

Suppose notes must now be stored in PostgreSQL. List the files you would add or change, and the files you would not need to touch.

Add a PostgresNoteRepository class implementing NoteRepository. Change repositoryFactory.ts to return it for a new store type, and config.ts if a connection string is needed. The routes, validation, app.ts and server.ts do not change, because they depend only on the interface and the factory. That short list of changes is the practical meaning of low coupling.

The config object is a Singleton. Give one benefit of that here and one risk that Singletons carry in general.

Benefit: the environment is read and interpreted once, so every part of the program agrees on the port, store type and version, and there is one place to look when a setting is wrong. Risk: a Singleton is shared global state. Code that reaches for it directly is harder to test with different settings, and if it were mutable, one part of the program could change behaviour for every other part. Freezing the object removes the second risk but not the first.

createApp() takes the repository as a parameter instead of calling the factory itself. What does that make possible?

It lets the caller decide which repository the application uses. Production passes whatever the factory built from configuration. Any other caller can pass a fresh in-memory repository, or a fake one that fails on purpose, and get a complete application around it without changing any application code.
